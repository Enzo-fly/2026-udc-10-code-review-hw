### 2. [К3] [critical] Ім'я файлу від користувача йде в `readFile` без нормалізації та перевірки теки

- **Де:** `app/src/imports.js:18` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  const text = await readFile(path.join(uploadDir, fileName), "utf8");
  ```
- **Чому це порушення:** За описом PR `fileName` — це «ім'я, з яким його завантажили», тобто значення від користувача. `path.join` нормалізує `..`, тож `fileName = "../../app/src/db.js"` або `"../../../etc/passwd"` читає довільний файл поза `uploads/`. Його рядки (після першого) розбиваються по комі й записуються в `db.members` як `name`/`email`/`phone`, після чого вміст стає доступним через `listMembers` (імена) і `memberCard` (email/телефон) — витік вмісту файлів сервера. Немає ні `path.resolve`, ні перевірки `startsWith(uploadDir + path.sep)` / `path.relative`. Додатково параметр `{ uploadDir }` дозволяє викликачу підмінити саму дозволену теку. Тестів із `../`, абсолютним шляхом і `%2e%2e`, яких вимагає К3, немає.
- **Що виправити:** `const target = path.resolve(UPLOAD_DIR, fileName); if (path.relative(UPLOAD_DIR, target).startsWith("..") || path.isAbsolute(path.relative(UPLOAD_DIR, target))) throw …;` (або `target.startsWith(UPLOAD_DIR + path.sep)`); краще приймати лише `path.basename(fileName) === fileName`. Не відкривати `uploadDir` як публічний параметр (або винести в тестову фабрику). Додати тести на відмову для `../x.csv`, абсолютного шляху та `%2e%2e/x.csv`.

### 3. [В5] [high] Рядки CSV не валідуються: неповні, порожні чи з комою в лапках рядки тихо записуються в учасників

- **Де:** `app/src/imports.js:19-24` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  const [, ...rows] = text.trim().split(/\r?\n/);
  let added = 0;
  for (const row of rows) {
    const [name, email, phone] = row.split(",");
    db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
  ```
- **Чому це порушення:** В5 вимагає валідувати дані ззовні до використання. Сценарії на звичайних файлах від громади: (а) порожній рядок посеред файлу → учасник з `name: ""`, `email: undefined`, `phone: undefined`; (б) `"Шевченко, Тарас",t@example.invalid,+380…` → `name = "\"Шевченко"`, `email = " Тарас\""`, телефон потрапляє в `email`-позицію — зсунуті поля без помилки; (в) рядок без телефону чи з невалідним email записується як є; (г) перший рядок відкидається без перевірки, що це справді заголовок `name,email,phone` — файл без заголовка втрачає першу людину. Результат — пошкоджені записи учасників, а `added` звітує про «успіх».
- **Що виправити:** Перевірити заголовок; парсити CSV з урахуванням лапок; для кожного рядка вимагати рівно 3 непорожні поля, валідний email і телефон; невалідні рядки відхиляти (повертати `{ added, rejected: [{ line, reason }] }` або кидати помилку до будь-якого запису). Додати тести на порожній рядок, кому в лапках, неповний рядок.

### 4. [В8] [medium] Id нового учасника береться з розміру колекції — дублікати після видалення чи непослідовних id

- **Де:** `app/src/imports.js:23` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
  ```
- **Чому це порушення:** В8: id генеруються лічильником або від наявного максимуму, а не з розміру колекції. Сценарій: з засіяних 5 учасників видалено учасника з id 2 (лишилось 4 записи, max id = 5) → імпорт дає новому учаснику `id: 5`, який уже належить «Марко Приклад»; `findMember(5)` повертає першого збігу, позики й журнал доступу (`accessLog`) прив'язуються не до тієї людини. Сусід у `db.js` робить інакше: `addLoan` використовує лічильник `nextLoanId++`. На засіяних даних (id 1…5 підряд) не проявляється, тому `medium`.
- **Що виправити:** Додати в `db.js` `addMember(member)` з лічильником `nextMemberId` (ініціалізованим від `Math.max(...members.map(m => m.id)) + 1`) за зразком `addLoan` і викликати його з імпорту. Тест: видалити учасника, імпортувати, перевірити унікальність id.

### 5. [В8] [medium] Повторний імпорт того самого файлу створює дублікати учасників

- **Де:** `app/src/imports.js:21-25` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  for (const row of rows) {
    const [name, email, phone] = row.split(",");
    db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
    added++;
  }
  ```
- **Чому це порушення:** В8: повторний виклик не повинен створювати дублікатів. Адміністратор повторно завантажує `new-members.csv` (наприклад, після таймауту) → кожна людина з'являється двічі з різними id і тим самим email; так само рядок з email наявного учасника (`olya@example.invalid`) створює другий запис. Нічого не перевіряє наявність email у `db.members`.
- **Що виправити:** Перед записом перевіряти унікальність email (зібрати `Set` наявних email один раз до циклу, щоб не отримати O(n·m)); дублікати пропускати або повертати в `rejected`. Тест: два імпорти поспіль → `added` другого = 0, кількість учасників не змінилась.
