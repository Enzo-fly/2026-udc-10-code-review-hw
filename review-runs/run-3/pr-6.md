### 2. [К3] [critical] Ім'я файлу від користувача йде в `readFile` через `path.join` без перевірки, що шлях лишився в `uploads/`

- **Де:** `app/src/imports.js:18` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  const text = await readFile(path.join(uploadDir, fileName), "utf8");
  ```
- **Чому це порушення:** За описом PR `fileName` — «ім'я, з яким його завантажили», тобто значення від користувача. `path.join` не нормалізує вихід за межі теки: `fileName = "../../etc/passwd"` або `"../app/src/db.js"` дає шлях поза `uploads/`, а абсолютний шлях на Windows (`"C:\\..."`) чи `..\\` теж не відхиляється. Будь-який файл, доступний процесу, буде прочитаний і розібраний як CSV, а його рядки записані в `db.members` (вміст стає видимим через `listMembers`/`memberCard`). Додатково опція `uploadDir` дозволяє викликачу підмінити саму дозволену теку. Тестів з `../`, абсолютним шляхом чи `%2e%2e` немає.
- **Що виправити:** `const target = path.resolve(UPLOAD_DIR, fileName); if (path.relative(UPLOAD_DIR, target).startsWith("..") || path.isAbsolute(path.relative(UPLOAD_DIR, target))) throw …;` (або перевірка `target.startsWith(UPLOAD_DIR + path.sep)`), відхиляти імена з роздільниками шляху; додати тести на `../`, абсолютний шлях і `%2e%2e`, що очікують відмову.

### 3. [В5] [high] CSV розбирається через `split(",")` без валідації рядків і заголовка

- **Де:** `app/src/imports.js:19-23` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  const [, ...rows] = text.trim().split(/\r?\n/);
  let added = 0;
  for (const row of rows) {
    const [name, email, phone] = row.split(",");
    db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
  ```
- **Чому це порушення:** В5 — дані ззовні валідуються перед використанням. Сценарії на звичайних файлах від громади: (а) поле в лапках з комою `"Петренко, Оля",olya2@example.invalid,+380000000020` → `name = "\"Петренко"`, `email = " Оля\""`, `phone = "olya2@example.invalid"` — учасник записаний зі зсунутими полями; (б) порожній рядок посередині файлу → учасник з `name = ""`, `email = undefined`, `phone = undefined`; (в) рядок з меншою кількістю колонок або з іншим порядком колонок у заголовку тихо записується; (г) email/телефон не перевіряються взагалі. Невалідний рядок не відхиляється, а тихо потрапляє в сховище.
- **Що виправити:** Перевірити заголовок (`name,email,phone`), розбирати CSV з урахуванням лапок (або явно заборонити лапки/коми й відхиляти такі рядки), пропускати/відхиляти порожні рядки, перевіряти кількість полів, непорожнє ім'я, формат email і телефону; повертати список відхилених рядків. Додати тести на кожен із цих випадків.

### 4. [В8] [medium] id нового учасника береться з розміру колекції; повторний імпорт дублює людей

- **Де:** `app/src/imports.js:23` (hunk `@@ -0,0 +1,27 @@`)
- **Цитата:**
  ```js
  db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
  ```
- **Чому це порушення:** В8 — id генеруються лічильником або від максимуму, а не з розміру колекції. Якщо перед імпортом видалено учасника (напр. id 2 із засіяних 1–5), `length + 1 = 5` — новий учасник отримує id 5, який уже має Марко; `findMember(5)` повертає першого збіглого, а позики Марка «належать» обом. Так само в `db.js` позики використовують окремий лічильник `nextLoanId`, а не `loans.length`. Крім того, повторний виклик з тим самим файлом (повтор завантаження) додає тих самих людей удруге — перевірки унікальності email немає.
- **Що виправити:** Генерувати id від `Math.max(...db.members.map((m) => m.id)) + 1` або додати в `db.js` метод `addMember` з лічильником (як `addLoan`); пропускати/відхиляти рядки з email, який уже є в `db.members`. Тест: імпорт після видалення учасника й повторний імпорт того самого файлу.
