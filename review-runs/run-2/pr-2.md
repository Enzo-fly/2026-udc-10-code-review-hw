## Знахідки

### 1. [К2] [high] Звіт віддає email учасників без жодного запису в журнал доступу

- **Де:** `app/src/loans.js:54` (hunk `@@ -46,15 +46,16 @@ export function lateFee(loan, onIso) {`)
- **Цитата:**
  ```js
  +      email: db.findMember(l.memberId)?.email ?? null,
  ```
- **Чому це порушення:** К2 вимагає, щоб функція, яка повертає email учасника, викликала `logAccess(db, user, memberId, purpose)` — по одному запису на кожного учасника, чиї дані віддано. `overdueReport` тепер повертає email, але `logAccess` у `loans.js` не імпортовано й не викликано. Сценарій: бібліотекарка (id 3) викликає `overdueReport(db, iryna, "2026-10-08")` → отримує email Марка (id 5), Тараса (id 2) та Олі (id 1), а `db.accessLog` лишається `[]`. Аудит доступу до персональних даних зламано; на відміну від сусідньої `memberCard` (`app/src/members.js:16`), яка логує кожне читання.
- **Що виправити:** імпортувати `logAccess` з `./audit.js` і для кожного **унікального** `memberId` у звіті викликати `logAccess(db, user, memberId, "overdue-report")` (один запис на учасника, а не на позику). Додати тест, що після виклику `db.accessLog.map(({ by, memberId, purpose }) => [by, memberId, purpose])` дорівнює очікуваному списку.

### 2. [К4] [high] Форматований рядок грошей «грн» з `toFixed` у відповіді API

- **Де:** `app/src/loans.js:58` (hunk `@@ -46,15 +46,16 @@ export function lateFee(loan, onIso) {`)

- **Чому це порушення:** К4: гроші в API — лише цілі копійки в полях `…Kopecks`; жодного форматування («15,00 грн»), дробів, `toFixed` чи `/ 100` у `src/`. Тут додано всі три заборонені конструкції. Сценарій: позика 6 → `feeKopecks: 11000` і паралельно `feeText: "110,00 грн"` — клієнти починають покладатися на рядок з локалізованим форматом, дробова арифметика з'являється в `src/`, а формат відображення зашивається в API. Про це поле опис PR мовчить.

### 3. [В9] [medium] Прибрано індекс `names`; лінійний пошук учасника двічі на кожну позику

- **Де:** `app/src/loans.js:53-54` (hunk `@@ -46,15 +46,16 @@ export function lateFee(loan, onIso) {`)
- **Цитата:**
  ```js
  -  const names = new Map(db.members.map((m) => [m.id, m.name]));
  ...
  +      member: db.findMember(l.memberId)?.name ?? "—",
  +      email: db.findMember(l.memberId)?.email ?? null,
  ```
- **Чому це порушення:** В9: відмова від наявної мапи та повторне обчислення того самого в циклі. `db.findMember` — це `members.find(...)` (`app/src/db.js:42`), тобто O(M). До зміни побудова імен була O(M + L) (одна мапа, пошук O(1) на рядок); після — O(L·M), причому з подвоєнням (два `findMember` на ту саму позику). Також `lateFee` тепер обчислюється двічі на рядок. На реалістичних обсягах громадської бібліотеки (≈5 000 учасників, ≈2 000 прострочених позик) це ~20 млн порівнянь на один звіт замість ~7 000 операцій — помітно для звіту, який зростає разом із позиками й учасниками.
- **Що виправити:** залишити мапу, але зберігати весь запис: `const members = new Map(db.members.map((m) => [m.id, m]));`, у `map` один раз взяти `const m = members.get(l.memberId);` і з нього `name`/`email`; `lateFee` обчислювати один раз.
